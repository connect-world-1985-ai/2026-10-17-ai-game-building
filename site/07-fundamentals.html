Page 7 · How games work

Game fundamentals, for an engineer who has never made a game

A game is a real-time simulation that reads input, updates a world many times per second, and redraws it. Everything else (sprites, physics, menus, saving) hangs off that loop. This page explains each building block with diagrams and four toys you can play with, and ends with why these are exactly the places where agent-made games tend to fall short.

Mental model for a backend engineer

Think of a game as a server with a 16-millisecond SLA and one very picky client. Each "request" is a frame: read input, advance the simulation by a time step, render. Miss the deadline and the client sees stutter. Unlike a web request, frames are not independent: a bug that moves an object 1 pixel too far each frame becomes a visible problem within a second. The game loop and delta time

Every game, from a Canvas toy to Unreal, runs some version of this loop. In the browser, requestAnimationFrame calls your function once per display refresh (usually 60 Hz, but 120 or 144 Hz on many laptops and gaming monitors) and pauses in background tabs. MDN: requestAnimationFrame Verified

Delta time (dt) is the time since the last frame. If you move an object "3 pixels per frame", it moves twice as fast on a 120 Hz screen as on a 60 Hz screen. Multiplying by dt ("180 pixels per second × dt") fixes speed, but a variable dt makes physics slightly different on every machine and can explode after a long pause. The usual answer is a fixed timestep with an accumulator: simulate in constant steps (for example 1/60 s or 1/120 s), render whenever a frame is due, and interpolate. This pattern is described in Glenn Fiedler's classic article "Fix Your Timestep!" and in Robert Nystrom's Game Programming Patterns: Game Loop. Practice

Interactive demo needs JavaScript.

Try it: drag the frame rate down to 20 fps. The orange "per frame" ball slows to a third of its speed; the blue and green balls keep 180 px/s. Turn on lag spikes and switch off "Clamp dt": the delta-time ball teleports after each hitch, while the fixed-step ball catches up in several small steps. Fixed steps also make the simulation deterministic (same inputs give the same result), which matters for replays, networking and automated tests (see page 10). Inference

// minimal fixed-timestep loop (browser)
const STEP = 1 / 120; let acc = 0, last = performance.now();
function frame(now) {
  acc += Math.min((now - last) / 1000, 0.25);  // clamp: avoid the "spiral of death"
  last = now;
  while (acc >= STEP) { update(STEP); acc -= STEP; }
  render(acc / STEP);                           // interpolation factor 0..1
  requestAnimationFrame(frame);
}
requestAnimationFrame(frame);

Input handling

Games usually poll input state once per update ("is Left held right now?") rather than reacting to each event, because the simulation runs on its own clock. Browser key events update a small keys map; the update reads it. Three details matter for feel: Practice

  • Edges, not just levels. "Jump" should fire when the key goes down, not every frame while it is held. Track "pressed this frame" separately from "held".
  • Focus and default actions. Arrow keys and Space scroll the page unless the game canvas has focus and calls preventDefault(). That is why the demos on this site ask you to click them first.
  • Many devices. Keyboard, mouse, touch (on-screen buttons) and gamepads (Gamepad API, which must be polled each frame) should map to the same abstract actions: left, right, jump. Engines such as Godot call this an "input map". Verified

State machines

Most game logic is "what am I doing now, and what can I switch to?". A finite state machine makes that explicit: a player is idle, running, jumping, falling or dead, and each state handles input differently. The same idea runs the whole game: title → playing → paused → game over. Without it, code fills up with flags like isJumping && !isDead && !isPaused, a classic source of bugs in quickly generated games. Game Programming Patterns: State Practice

Collision and physics

Collision has two halves: detection (do these shapes overlap?) and response (what happens: push apart, bounce, take damage, collect). Most 2D games use simple shapes: axis-aligned bounding boxes (AABB), circles, and tile grids. Rotated polygons use the separating axis theorem (SAT). Many objects also need a broad phase, such as a spatial grid, so you do not test every pair. MDN: 2D collision detection Verified

Interactive demo needs JavaScript.

The tunneling tab shows a real, common bug: a fast object moves 30 pixels per frame and a wall is 10 pixels thick, so most frames simply never overlap the wall. Fixes are sub-stepping (split each move into small steps), swept tests / ray casts, or a physics engine's continuous collision detection (CCD). Rapier, for example, documents CCD as an opt-in per body. Rapier docs: CCD Verified

Physics engine or hand-written movement?

A physics engine (Rapier, Box2D, Matter.js, cannon-es) simulates forces, mass, friction and joints. That is great for stacking crates, ragdolls, pinball, or a car with suspension. But platformer heroes usually use a kinematic controller: hand-written velocity and collision rules, because players expect instant, unrealistic control (stop on a dime, change direction mid-air). Both Godot (CharacterBody2D) and Unity (CharacterController) ship kinematic controllers for exactly this reason. The platformer demos on this site use a hand-written controller. Practice

Tilemaps

Levels in 2D games are usually grids of tile indices: 0 = empty, 1 = grass top, 2 = dirt, and so on. Each index points into a tileset image. Collision can come straight from the grid ("is tile (x, y) solid?"), which is cheap and has none of the tunneling problems of free shapes at normal speeds. Editors such as Tiled and LDtk save maps as JSON or XML that engines import (see page 5). Verified

Cameras

A camera decides which part of the world is on screen. Good cameras are subtle: Practice

  • Smoothing: move a fraction of the remaining distance each frame (cam += (target − cam) × (1 − e−k·dt)), so the view eases instead of snapping. Write it with dt or it behaves differently at 144 Hz.
  • Look-ahead and dead zone: show more space in the direction of travel; ignore small movements so the screen does not jitter.
  • Bounds: never show outside the level.
  • 3D chase camera: follow behind and above the car, lag slightly in turns, look at a point ahead of the car. Try toggling smoothing in the racer demo.

Itay Keren's GDC 2015 talk "How Cameras in Side-Scrollers Work" (also known as "Scroll Back") is the standard reference for 2D cameras. Practice

Sprite animation

2D animation is usually a flipbook: a sprite sheet holds frames in a grid; the game shows frame n for some milliseconds, then frame n+1. The current animation is chosen by the state machine (idle, run, jump). Flipping the image horizontally gives a left-facing version for free. Many frames are packed into one texture atlas so the GPU can draw them in one batch. Practice

This is the hardest asset type for AI image generation: a model must draw the same character in 6–12 poses with matching proportions, palette and pixel grid. Page 2 covers the tools that try. In the platformer demo the CC0 sprite mode uses two Kenney frames for the walk cycle; the code-drawn mode fakes motion with a small bob. Inference

Enemy AI

"Game AI" has little to do with machine learning. It is mostly simple rules that create readable, fair behaviour: Practice

  • Patrol: walk until a wall or ledge, turn around (the demo's purple enemies do exactly this).
  • State machines: patrol → notice player → chase → attack → return.
  • Behaviour trees: composable decision trees used in larger games (Unreal has a built-in editor).
  • Steering behaviours: seek, flee, arrive, avoid, used for flocks and racing opponents following a racing line.
  • Pathfinding: A* on a grid or navigation mesh. Red Blob Games: Introduction to A* is the best visual explanation.

The design goal is "fun to play against", not "optimal". An enemy that always aims perfectly is frustrating. Agents happily generate clever AI, but tuning it to be fair requires playing. Inference

Level design

Good levels teach one idea at a time in a safe place, then test it with danger, then twist it. A common shorthand is "introduce, develop, twist, conclude", widely discussed in analyses of Nintendo's level design, for example Game Maker's Toolkit on Super Mario 3D World. Practice

For agent-built games the practical advice is: keep levels as data (text grids, JSON, Tiled files), not as code; ask for a level validator (is every gap jumpable with the current jump height? is the goal reachable?), and design the first level yourself or with the agent in small steps. Procedural levels (random rooms, noise terrain) are easy to generate but hard to make interesting. Inference

UI, menus, saving and audio

UI and menus

HUD (score, health), title screen, pause, settings, game over. On the web you can draw UI on the canvas or put HTML on top; HTML is easier for agents and screen readers. Plan for different screen sizes from the start.

Saving

Serialize state to JSON with a version number. Browsers: localStorage or IndexedDB. Some browsers restrict storage for pages opened from file://, so test saves on the real host. Desktop engines write files to a user data folder.

Audio

Browsers block sound until the user interacts (autoplay policy), so start the AudioContext on the first click or key. Keep separate volumes for music and effects, and limit how many copies of one effect play at once. MDN autoplay guide

Game feel ("juice")

Two games with identical rules can feel completely different. "Game feel" is the moment-to-moment sense of control: how quickly the hero responds, how forgiving jumps are, how impacts land. The vocabulary comes from Steve Swink's book Game Feel (2008) and the talk "Juice it or lose it" (Martin Jonasson and Petri Purho, 2012). Platformer techniques are well documented by their designers, for example Maddy Thorson's "Celeste & Forgiveness", and Kyle Pittman's GDC talk "Building a Better Jump". Practice

Why agent-made games often fall short here

Coding agents are good at the parts of games that look like ordinary software: a loop, classes, a tile parser, a menu. The weak spots are where quality is felt over time rather than visible in one screenshot or one test. This is the author's synthesis from the fundamentals above and from the examples on page 11.
