How AI agents build 2D and 3D games

An evidence-based guide for an experienced Windows engineer who has never made a game. It covers where game assets come from, which engines agents work well with, the fundamentals every game needs, two worked examples, how agents test games, what "one prompt" games really involve, and how to publish legally.

The answer in seven points
  1. A coding agent can build a playable small game from one short prompt today. The best-documented case is a 7-line prompt that produced a 3D browser game with tests and seven commits. Its author called the result "not a good game". Verified (page 11)
  2. A language model alone writes code and text, nothing else. It can also "draw" with code (Canvas, SVG, procedural meshes, synthesised sound). Raster images, 3D models from images, music and voices need external tools, reached through an API script, a CLI or an MCP server. Verified (page 1)
  3. The cheapest good path is code-drawn art first, then free CC0 packs, then AI art only for a unique look. AI art's real cost is consistency and cleanup, not the price per image. Inference (pages 2–4)
  4. For agents, text-based stacks win: plain Canvas or Phaser 4 for 2D on the web, Three.js for 3D on the web, Godot 4 for desktop. Unity, Unreal and Roblox now offer official MCP access, with more friction. Inference (page 5)
  5. Agents must be given eyes. Expose game state as text, control time, take screenshots. Even then, benchmarks show agents solve about half of realistic game-dev tasks and find about half of real bugs. Verified (page 10)
  6. Fun is still your job. Movement feel, level design and "is this fun?" need a human playing the game. Practice (page 7)
  7. Legal basics are manageable: use original characters (mechanics are free, Nintendo's expression is not), keep a CREDITS.md, disclose AI content where stores ask, and expect raw AI output to have weak copyright protection. Verified (page 12)

How to read the evidence labels

LabelMeaning
VerifiedChecked against a primary source: official docs, a repository, a paper, a court document, or the author's own post.
PracticeWidely documented practitioner practice, or a vendor demo with public artifacts that is plausible but not independently reproduced.
InferenceThe author's reasoning from the evidence. Time estimates and recommendations carry this label.
UnverifiedReported or marketed but not confirmed; includes vendor and host claims marked "Promotional".
ExperimentalWorks in demos or research but is not yet dependable for shipping.
